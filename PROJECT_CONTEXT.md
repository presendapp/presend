## Mission
Presend propose des micro-outils IT gratuits, respectueux de la vie privée, sans inscription : à la fois des outils navigateur (rien n'est jamais envoyé à un serveur) et une API REST server-side gratuite.

## Les trois volets du projet
1. **Produit** : le site + l'API + les outils navigateur (voir STRUCTURE.md).
2. **Distribution** : campagne de démarchage GitHub ciblé (voir ROADMAP.md pour l'état exact), soumissions RapidAPI/npm/Postman/MCP registry, annuaires "awesome-*".
3. **Recherche de sécurité / bug bounty** (volet séparé mais mené par la même personne) : divulgations responsables sur des projets tiers (RunOnFlux, GitLab, Vercel, Cosmos SDK/Immunefi...). Voir ROADMAP.md pour l'état des divulgations en cours.

## Stack technique
- Frontend : HTML/CSS/JS statique, Cloudflare Pages
- Backend : Cloudflare Pages Functions (functions/api/*.js) — **pas** de Workers autonomes, donc pas de cron triggers natifs disponibles
- API : OpenAPI 3.0 (openapi.json = source de vérité, tout le reste doit être régénéré/vérifié depuis ce fichier)
- Analytics/rate-limit : Cloudflare KV (env.PRESEND_ANALYTICS)
- SEO : scripts Python (daily_seo.py, gsc_*.py, generate-rss.py)

## Leçons importantes déjà apprises (ne pas refaire ces erreurs)
1. **Licence Spamhaus** : les données DROP sont libres d'usage, mais le **nom "Spamhaus" est interdit en matériel marketing/promotionnel** (section 3.2 de leurs conditions). OK dans une réponse API technique ou une FAQ factuelle ; interdit dans un titre SEO, une accroche, ou un message de démarchage. Reformuler en "a curated netblock reputation list" dans ces contextes.
   - Complément (25 sept.) : la correction du 24 sept. avait oublié `openapi-security-only.json` et l'export RapidAPI `presend-openapi.json` (titre "IP reputation check (Spamhaus DROP)"). Vérifier par un scan des champs summary/description/title de TOUS les JSON (repo + rapidapi-exports) plutôt que de se fier à la mémoire. Côté usage des données : téléchargement automatisé au plus 1 fois/heure (1 fois/jour suffit), crédit à The Spamhaus Project + date/copyright avec les données -- `ip-reputation` respecte les deux depuis le 25 sept. Précision (26 sept., après relecture) : ces exigences ne sont PAS dans la page des conditions (`/drop/terms/`, qui dit surtout « gratuit » + nom interdit en marketing, 3.2) mais dans la FAQ DROP (« Who should use the DROP list? ») : crédit à The Spamhaus Project dans un produit, date/copyright conservés avec les données, mises à jour automatisées, **pas plus d'un téléchargement par jour** (une autre réponse dit « au moins une heure d'intervalle » : on applique la plus stricte). `ip-reputation` rafraîchit donc désormais toutes les 24 h (12 h avant), `stale` au-delà de 48 h. Toujours citer la FAQ, pas les conditions.
   - Complément (25 sept., soir) : 2 PR promotionnelles nommaient encore Spamhaus (awesome-mcp-servers #14651, awesome-osint #1178) -- corrigées. MAIS le nom est légitime (et même requis pour l'attribution) dans un texte technique : une substitution automatique a rendu absurde la note de conception guard-core #119, restaurée à l'identique 2 minutes plus tard depuis /tmp/guardcore_note.md. Toujours trier promotionnel / technique au cas par cas.
   - Règle pour tout script de correction publique en masse : confirmation PUBLICATION PAR PUBLICATION avec le texte complet affiché, jamais une confirmation globale après un aperçu tronqué. Garder une copie locale de chaque texte d'origine avant de le modifier.
2. **`maintainer-change-check` est actuellement npm-only** -- ne pas prétendre qu'il couvre PyPI ou crates.io (erreur déjà commise une fois, corrigée publiquement ; le 25 sept. elle subsistait encore dans 3 issues -- SkillSpector #602, devguard #3083, typomania #36 -- corrigées. Chercher avec `gh api search/issues -f q='author:presendapp ...'` plutôt que de supposer qu'une correction est complète).
3. **Ne pas proposer les endpoints "wrapper"** (`ip-reputation`, `url-reputation`, `malware-check`) à des outils de sécurité matures — ils intègrent très souvent déjà Spamhaus/URLhaus/MalwareBazaar en direct. Ces trois retours sont arrivés indépendamment (IntelOwl, web-check) : vérifier avant de pitcher, privilégier `maintainer-change-check`/`typosquat-check`/`address-risk`/`tx-decode`/`supply-chain-check` comme vrais différenciateurs.
   - Complément (25 sept., guard-core) : avant de proposer un endpoint qui ne fait que relayer un jeu de données **gratuit et petit** (ex. `ip-reputation` = Spamhaus DROP, ~110 Ko), se demander si la cible ne ferait pas mieux de le charger en local. Pour un middleware appelé à chaque requête, un appel à Presend ajoute latence, point de panne et envoi des IP de visiteurs à un tiers (donnée personnelle). Dans ce cas, le dire franchement et proposer le design natif, quitte à ce que Presend sorte de la boucle.
4. **`address-risk` couvre EVM et Bitcoin depuis le 26 sept., jamais Cosmos SDK (bech32 -> `sanctioned: null`, OFAC n'en publie aucune)** (avant le 26 sept. : EVM seulement) — deux fois découvert en pitchant (Bitcoin wallet, dYdX v4). Vérifier l'écosystème cible avant de proposer.
   - Complément (26 sept.) : l'API **reconnaît** le format bech32 mais renvoie `sanctioned: null` (non vérifié, pas « propre »). La description du paramètre disait « EVM ... or Cosmos SDK bech32 address to check » dans 5 fichiers (openapi.json, openapi-blockchain.json, mcp.js, 2 exports RapidAPI) : corrigé. Toute description (outil ET paramètres) doit refléter la limite réelle.
5. **Cloudflare Pages Functions n'a pas de cron trigger natif** (feature Workers uniquement) — pour toute tâche planifiée, chercher une alternative (service tiers, déclenchement manuel) plutôt que de supposer que c'est faisable directement.
6. **Cloudflare Workers/Pages n'expose pas les détails de certificat TLS** (émetteur, expiration) au niveau JS, même via l'API `connect()` — un vérificateur SSL détaillé n'est pas réalisable proprement sur cette stack.
7. **Toujours vérifier les conditions d'usage commercial** avant d'adopter un service tiers gratuit (UptimeRobot restreint son palier gratuit au non-commercial depuis nov. 2024 — BetterStack et StatusCake n'ont pas cette restriction).
8. **Tester un check heuristique sur un lot de paquets populaires SAINS avant de le pitcher ou de l'intégrer** : typosquat-check signalait 12/25 paquets npm très populaires (ms, qs...), maintainer-change-check 17/22 (passations légitimes anciennes). Ni l'un ni l'autre n'avait été testé sur des dépendances réelles. Dans un outil qui scanne un vrai package.json, ce bruit rend le signal inutile. Corrigé le 25 sept. -- garder le jeu de test (25 paquets npm + 10 PyPI légitimes, 18 typosquats, rejeu event-stream au 2018-11-26).
   - Complément (26 sept.) : ce jeu de test n'avait jamais été enregistré (perdu avec /tmp). Désormais versionné dans `tests/typosquat/` : `run.mjs` (hors ligne : ~180 légitimes, 27 typosquats, normalisation PyPI), `top-pypi.mjs` (top 15 000 PyPI) et `top-npm.mjs` (~17 000 npm-high-impact), qui échouent si un paquet populaire est signalé sans avoir été revu. Faux positifs sur paquets populaires ramenés de 58 à 11 (PyPI) et de 65 à 1 (npm), tous voulus. Tout ajout à `POPULAR` doit passer ces trois tests ; un nom légitime qui ressemble à une cible va dans `KNOWN_LEGIT` (après vérification du dépôt et de l'historique), pas en retirant la cible.
9. **maintainer-change-check ne détecte QUE le schéma event-stream** (nouveau publieur après dormance). Ne jamais citer ua-parser-js (compte légitime piraté) ni colors.js (sabotage par le mainteneur d'origine) comme exemples : même identité de publieur, donc invisibles. L'affirmation inverse figurait dans 11 publications, corrigées le 25 sept. -- **mais pas partout** : le 26 sept., un scan exhaustif l'a encore trouvée dans le README du profil, les README de presend-check-action et presend-examples, la release v2.0.0 (avec "Nothing else free does this", faux : npq le fait) et la description RapidAPI, plus un "npm/PyPI ... maintainer-change" chez Arnon-hs #9 et "Spamhaus DROP ... unlike every" dans la release v1.9.0 de presend-api. Tout corrigé (originaux dans `archive/corrections_2026-09-26/`). Une correction ne vaut que si elle couvre corps d'issues, NOS COMMENTAIRES, README, releases et exports : `python3 scripts/claims-audit.py`.
   - Complément (26 sept.) : ce schéma est AUSSI celui des passations légitimes (reprise de l'écosystème Express par son comité technique, ljharb...). Règle ajoutée : un nouveau publieur qui maintient déjà un autre paquet à 100 000+ téléchargements/semaine (hors paquet évalué) est rapporté dans `established_publisher_events`, sans `suspicious`. Contournable par un attaquant ayant déjà repris un paquet populaire (signal de tri, pas une garantie). L'API de recherche npm (`/-/v1/search?text=maintainer:X`) coupe après ~10 requêtes rapides (HTTP 429) : toujours prévoir cache et repli prudent. Mesure : `tests/maintainer-change/top-npm.mjs`.
   - Complément (26 sept., soir) : l'exemption "CI" se fondait sur le NOM du compte (bot, ci, release...), contournable en s'appelant `foo-release`. Désormais seul `_npmUser.trustedPublisher` (posé par le registre lors d'une publication OIDC) exempte. Règle générale : pour toute exemption dans un contrôle de sécurité, n'accepter qu'un signal que l'attaquant ne contrôle pas. Test hors ligne de la porte dérobée : `tests/maintainer-change/unit.mjs`.
10. **Toute écriture KV doit être échantillonnée** (modèle : écriture 1 fois sur N avec +N). L'espace `PRESEND_ANALYTICS` est partagé par tous les endpoints (rate limits, stats, copie Spamhaus) et le plan gratuit Cloudflare plafonne KV à 1 000 écritures/jour : un seul endpoint non échantillonné appelé à chaque page vue (`track.js`, corrigé le 25 sept.) peut épuiser le quota et désactiver en silence tous les rate limits. Toute écriture KV doit aussi être dans un try/catch qui ne fait jamais échouer la requête.
   - Limite de l'échantillonnage : il donne la bonne limite EN MOYENNE mais avec une forte variance quand la limite est basse. Sous 10/min avec +5 une fois sur 5, 2 écritures suffisent à bloquer : ~18 % des clients bloqués à tort au 5e appel (constaté le 25 sept. sur les tests du client npm). Pour les appels rares et coûteux (POST batch), compter exactement (+1 à chaque appel) : `checkRateLimit(..., exact = true)` dans typosquat-check et maintainer-change-check.
11. **Via MCP, "l'appelant" est notre propre serveur**, pas l'utilisateur ni même l'agent : tout endpoint qui se base par défaut sur l'IP, la géolocalisation ou les en-têtes de l'appelant donne un résultat faux s'il est exposé tel quel en MCP. Constaté le 25 sept. : `ip` renvoyait l'IP Cloudflare de Presend (retiré), `phone_verify` lisait 0612345678 comme un numéro suisse (le pays doit maintenant être fourni), `user_agent` sans `ua` échouait (`ua` désormais obligatoire). Pour tout nouvel outil MCP : aucune valeur par défaut dérivée de la requête.
12. **Cloudflare refuse le User-Agent par défaut de Python `urllib`** (`Python-urllib/3.x` -> 403, `error code: 1010`, Browser Integrity Check), sur tous les endpoints. `python-requests`, curl et Node passent. Constaté le 26 sept. A priori non réglable : c'est un réglage de zone, et `pages.dev` est la zone de Cloudflare, pas la nôtre (seul un domaine personnalisé le permettrait ; à confirmer dans le dashboard). Documenté pour les utilisateurs depuis le 26 sept. : `api.html#python-user-agent` + README. Tout client `urllib` (dont l'adaptateur tripwire prévu) doit envoyer un `User-Agent` explicite.
13. **Démarchage : ne jamais re-soumettre après un refus.** L'audit du 26 sept. (75 conversations sur 65 dépôts) a trouvé des re-soumissions faites avant la tenue de ces fichiers : lissy93/awesome-privacy (refus, re-soumission, réponse agacée), anondotli/awesome-privacy-tools (entrée retirée puis ré-ajout annulé par le mainteneur, puis une nouvelle PR), public-apis (deuxième catégorie, contraire à leurs règles), APIs-guru (deux issues ouvertes pour la même demande). Toutes nettoyées le 26 sept. Désormais : `scripts/filter-candidates.sh` avant tout démarchage, `scripts/no-contact.txt` complété à chaque refus.
14. **Nos pages publiques divergent d'openapi.json sans que rien ne le signale.** Constaté le 26 sept. grâce à un mainteneur (rauthy #1737) : `api.html` ne documentait pas 9 endpoints (dont TOUS nos différenciateurs supply-chain) et n'avait aucun `id`, donc les ancres `#GET-api-...` de 16 messages de démarchage étaient mortes depuis leur envoi. Les corrections de compteurs du 25 sept. n'avaient touché que les chiffres, pas la liste. Règles : après tout ajout d'endpoint, comparer la liste de `api.html` à openapi.json (pas seulement le compteur) ; avant d'envoyer un lien, l'ouvrir une fois (`curl` + recherche de l'ancre). Les 7 traductions d'`api.html` ont encore 25 endpoints sur 52.
15. **Le bot SEO (`github-actions[bot]`, « daily SEO auto-update ») pousse chaque jour sur `main`** (`rss.xml`, état d'indexation) : faire `git pull --rebase` en début de session, sinon le premier push est refusé. Au passage : le dossier `archive/` cité dans ces fichiers est à la RACINE de `presend-project` (`~/Bureau/presend-project/archive/`), pas dans `microtools/`.
16. **Une source classée par actif n'est pas classée par chaîne.** L'OFAC range des adresses 0x sous USDT, USDC et ETC, pas seulement sous ETH/BSC/ARB. `address-risk` ne lisait que ces 3 listes et répondait `sanctioned: false` pour 4 adresses sanctionnées (constaté et corrigé le 26 sept., en voulant l'étendre à Cosmos). Règles : pour un contrôle de conformité, chercher dans TOUTES les listes et refuser de conclure si l'une manque (fail closed) ; `node tests/address-risk/lists.mjs` échoue si la source ajoute ou retire une liste. Plus généralement : avant d'étendre un contrôle, mesurer la couverture de l'existant sur les vraies données.
17. **Une promesse de confidentialité doit décrire TOUT le trajet de la donnée.** `password-breach` promettait partout que le mot de passe n'était « jamais transmis en entier » : vrai vers HIBP (préfixe SHA-1 de 5 caractères), faux vers Presend, puisque c'est un GET et que le mot de passe circule dans l'URL (historique, proxys, journaux). Corrigé le 26 sept. dans les 8 pages API, 3 openapi, mcp.js, la note de l'endpoint et le README npm ; `password-check` (POST) est désormais recommandé pour les vrais mots de passe. Motif ajouté à `claims-audit.py`.
18. **`node --check` ne détecte pas les erreurs de syntaxe de nos fonctions, et un build Cloudflare raté est silencieux.** Le 26 sept., une apostrophe non échappée dans une chaîne entre apostrophes (`'... request's URL ...'`) a cassé `password-breach.js` : `node --check` a répondu OK (vérifié ensuite sur la version cassée), le push a réussi, et Cloudflare a gardé en silence l'ancienne version de TOUT le commit (pages comprises). Seule la boucle de vérification en prod l'a révélé. Règles : valider avec `npx --yes acorn --ecma2022 --module --silent <fichier>` ; après chaque push, vérifier en prod le NOUVEAU comportement, pas un simple 200 ; dans le code, préférer les guillemets doubles ou les gabarits pour tout texte en anglais (apostrophes).

## Décisions business en attente / prises
- **Pas de palier payant RapidAPI pour l'instant** : décision consciente d'attendre d'avoir de vraies données d'usage avant de introduire du payant, pour rester cohérent avec le positionnement "gratuit" déjà largement communiqué.
- **Pas de gonflement artificiel des étoiles GitHub** : décision de laisser la croissance venir organiquement du travail de fond plutôt que d'acheter/échanger des étoiles.
- Le trafic `uuid` a un profil qui ressemble à du scan/bot automatisé (pics soudains, longs silences) — ne pas sur-interpréter le total cumulé comme de l'adoption organique réelle sans vérifier la répartition par jour.
